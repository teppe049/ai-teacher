Postgres で index を貼る基準

2026-06-14

一言でいうと: WHERE / JOIN / ORDER BY で頻繁に使い、かつ選択性が高い（値がバラけている）カラムに貼る。読み取りは速くなるが、書き込み（INSERT/UPDATE/DELETE）は index の数だけ遅くなるので貼りすぎ厳禁。

貼るべきカラムの判断軸

観点貼る価値
WHERE の絞り込み条件に頻出高い
JOIN のキー（特に外部キー）高い。Postgresは外部キーに自動でindexを貼らないので要手動
ORDER BY / GROUP BY の対象中〜高。ソート処理を省ける
選択性が高い（例: メールアドレス、ID）高い
選択性が低い（例: 真偽値、性別）低い。全体の数割がヒットするならindexよりseq scanが速い

選択性（カーディナリティ）が肝

「そのカラムで絞ったとき、どれだけ行が減るか」が index の効きを決める。boolean のように2値しかないカラムは、絞っても半分しか減らず、プランナは index を無視して全表スキャンを選ぶことが多い。「ほぼ一意」に近いほど index は効く。

複合インデックスの順番ルール

複数カラムをまとめて貼るときは順番が重要。等価比較（=）するカラムを左に、範囲比較（>, <, BETWEEN）やソート対象を右に。

-- status で絞って created_at でソートするクエリなら
CREATE INDEX idx_orders_status_created
  ON orders (status, created_at);

-- これは (status = ? ORDER BY created_at) に効く
-- 逆順 (created_at, status) だと status の絞り込みに使いづらい

左端のカラムから連続して使われる（left-most prefix）ぶんしか効かない点に注意。(a, b, c) の index は a、a,b、a,b,c には効くが、b 単独・c 単独には効かない。

貼りすぎるとどうなるか

  • 書き込みが遅くなる — INSERT/UPDATE/DELETE のたびに全 index を更新する。index 10個あれば書き込みコストもそれだけ増える。
  • ディスクを食う — index は実体を持つ。巨大テーブルでは index がテーブル本体より大きくなることも。
  • 使われない index が残る — 効くと思って貼ったが実際クエリが使っていない、というケース。

効いているか確認する

-- 実行計画を見る。Index Scan になっているか、Seq Scan か
EXPLAIN ANALYZE
SELECT * FROM orders WHERE status = 'paid' ORDER BY created_at DESC;

-- 使われていない index を洗い出す（idx_scan = 0 が候補）
SELECT relname, indexrelname, idx_scan
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC;

実務での進め方

  1. まず index なしで作り、遅いクエリを EXPLAIN ANALYZE で特定する。
  2. そのクエリの WHERE / JOIN / ORDER BY を見て候補を決める。
  3. 貼ったら本当に Index Scan に変わったか確認する。
  4. 定期的に pg_stat_user_indexes で「使われていない index」を掃除する。
推測で貼らない。遅いクエリを計測してから貼る。これが鉄則。
