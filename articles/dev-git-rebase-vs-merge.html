git rebase と merge の違い

2026-06-13

一言でいうと: merge は分岐を残したまま合流させる（履歴が二股に見える）。rebase は自分のコミットを相手の先端に付け替えて履歴を一本道にする（書き換え）。

イメージ

merge:  A---B---C  (main)
             \       \
              D---E---M  (feature をマージ。M がマージコミット)

rebase: A---B---C---D'---E'  (D, E を C の上に付け替え。一本道)

違いの要点

mergerebase
履歴分岐が残る一本道に書き換わる
コミットID変わらない付け替えで変わる（別物になる）
マージコミット増える増えない
コンフリクト1回まとめて解決コミット単位で順次解決
向いている場面共有ブランチ、経緯を残したい手元のブランチを整える、PR前に最新に追従

黄金律

すでにpushして他人が見ている（共有された）コミットはrebaseしない。

rebaseはコミットIDを書き換えるため、共有済みの履歴を書き換えると他人のローカルと食い違い、強制pushと巻き戻しの地獄になる。書き換えていいのは「まだ自分しか持っていないコミット」だけ。

よく使うコマンド

# feature を main の最新に追従させる（PR前の定番）
git checkout feature
git rebase main

# 途中で詰まったら
git rebase --abort        # 中止して元に戻す
git rebase --continue     # コンフリクト解決後に続行

# merge する場合
git checkout main
git merge feature

結局どっち

  • PRを出す前に自分のブランチをmainの最新に追従させる → rebase が綺麗。
  • mainに取り込む / 共有ブランチ同士 → merge が安全（経緯も残る）。
  • チーム方針があるならそれに従う。履歴を一本道にしたいチームは「rebase運用 + squash merge」が多い。
